# mpu6050_iio —— STM32MP157 上的 MPU6050 IIO 驱动 设计文档

日期:2026-09-22
作者:fyy0619-cell
状态:已确认,待实现

## 1. 背景与目标

作者刚学完 Linux 字符设备驱动,目标是 2027 年 3-4 月冲击高通(Qualcomm)嵌入式/内核方向实习。
本项目的定位是一个**体现工程思维、挂进内核子系统框架**的驱动,而非孤立的字符设备例程。

选择 **IIO(Industrial I/O)** 子系统:它与 V4L2 同源 —— 都是"统一设备模型 + 标准化用户空间 ABI + 可选缓冲/硬件触发数据流"的框架,但复杂度对刚入门者更友好,且高通手机 SoC 里 sensor 子系统占比很大,面试极对口。

目标硬件:**STM32MP157 PRO(100ASK)** + 真实 I2C 传感器 **MPU-6050/6500(6 轴 IMU)**。
MPU6050 数据率高、带 FIFO 和 DRDY 中断,能完整练到 IIO 的 buffer + trigger,与 V4L2 的 vb2 缓冲队列思想一一对应。

### 非目标(YAGNI)
- 不移植/修改内核主线 `inv_mpu6050`(仅作参考阅读)。代码自研,命名 `mpu6050_iio` 避免冲突。
- 首版不做 FIFO 批量水位中断、运动唤醒、DMP 等高级特性(列为后续 stretch)。

## 2. 实现路线决策

内核主线已有 `inv_mpu6050`。两条路:
- **A(采纳):从零手写精简版。** 吃透框架每一层,面试能逐行讲清"为什么这么写";把 `inv_mpu6050` 当参考资料读。
- B:移植/改内核驱动。快,但工程思维体现少,面试讲不深。

## 3. 架构分层

每层职责单一、接口清晰、可独立理解与测试。

1. **总线 / probe 层**
   - 注册 `struct i2c_driver`,靠设备树 `compatible = "invensense,mpu6050"` + `of_device_id` 匹配。
   - probe 中读 `WHO_AM_I`(寄存器 0x75,期望 0x68)校验芯片,唤醒(清 `PWR_MGMT_1` sleep 位),配置默认量程/采样率。
   - 寄存器访问统一走 **regmap**(`regmap_i2c`):量产写法,白得寄存器缓存与 debugfs regmap dump。

2. **设备模型层**
   - `devm_iio_device_alloc()` 分配 `struct iio_dev`;私有结构体存 `regmap *`、`mutex`、当前采样率与量程、irq。
   - `devm_iio_device_register()` 注册。全程 devm_ 资源管理,不手写 remove 释放路径(工程点)。

3. **通道层**
   - `iio_chan_spec[]`:accel x/y/z、anglvel(陀螺)x/y/z、temp,外加 timestamp 通道。
   - `info_mask_separate` = RAW;`info_mask_shared_by_type` = SCALE;`info_mask_shared_by_all` = SAMP_FREQ。
   - 实现 `read_raw` / `write_raw`;`scan_index` / `scan_type`(bits/storagebits/大小端)供缓冲扫描使用。

4. **缓冲 + 触发层(对标 V4L2 vb2 的核心)**
   - `iio_triggered_buffer_setup()` 挂 kfifo 缓冲 + 底半部 `pollfunc`。
   - **DRDY 硬件触发**:MPU6050 INT 脚 → STM32MP157 GPIO IRQ → `iio_trigger`。
   - 每次触发:pollfunc 用 `regmap_bulk_read` 一次性 burst 读使能的扫描通道,打时间戳,`iio_push_to_buffers_with_timestamp()` 入队。
   - 用户用 scan_mask 选择要哪些通道流式输出 —— 对应 V4L2 协商 format 的思想。

5. **设备树层**
   - MP157 I2C 节点:`reg = <0x68>`、`interrupt-parent` + `interrupts`(接 INT 的 GPIO)、可选 `vdd-supply` regulator。
   - 附一份 `invensense,mpu6050.yaml` binding 文档(额外工程加分)。

## 4. 数据流

- **sysfs 单次**:`cat in_accel_x_raw` → `read_raw(RAW)` → regmap 读 → 换算返回。
- **缓冲流式**:选通道(scan_elements)→ `buffer/enable=1` → DRDY 中断 → trigger → pollfunc burst 读 → 入 kfifo → 用户 `read()` `/dev/iio:deviceN`(或 `iio_readdev`)。

## 5. 错误处理

- probe:统一用 `dev_err_probe()`;WHO_AM_I 不符 → `-ENODEV`;regmap/irq/regulator 申请失败走 devm 自动清理。
- 运行时:i2c 读写错误层层上抛;`mutex` 保护"配置写"与"数据读"并发;缓冲仅扫描 scan_mask 选中的通道。
- 错误注入测试:错 I2C 地址 / 拔线 → probe 干净失败,不残留资源。

## 6. 里程碑(循序渐进降风险)

- **M1 板级 bring-up**:设备树节点 + i2c probe + WHO_AM_I + regmap 初始化,dmesg 看到设备。打通 VM/TFTP/NFS 交叉编译加载链路。
- **M2 raw 通道 + SCALE + 采样率**:纯 sysfs;`iio_info` 输出干净;静止时某轴 ≈ ±9.8 m/s² 验证量程换算正确。
- **M3 软件触发的 buffer**:先用 sysfs-trigger(软件触发)把 `iio_triggered_buffer` 管道打通,不碰中断,降低调试难度。
- **M4 真·DRDY 硬件触发**:GPIO 中断 → `iio_trigger` → burst 读 → 时间戳 → `libiio`(`iio_readdev`)流式验证。补 binding yaml 与 README 工程说明。

## 7. 测试策略

- `iio_info` 枚举通道/属性无误。
- sysfs 读取交叉验证:静止重力 ≈ 9.8 验证 accel scale;温度合理。
- `iio_readdev -b 64 iio:deviceN` 观察缓冲吞吐是否匹配设定采样率。
- 错误注入:错地址 → probe 失败且无资源泄漏(可配合 debugfs / lsmod 卸载复检)。
