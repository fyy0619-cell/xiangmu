二、read_raw 到底干嘛、为什么非要它(重点)

这是最容易糊涂、也最关键的一个点。一句话:read_raw 是"真正去芯片里把数值取出来"的那个函数。框架负责接待客人,但它不会读你这颗芯片——只有你写的 read_raw 会。

  • IIO 框架 = 服务员:负责"客人点菜(cat 属性)"和"上菜(格式化返回)"。这套通用流程(fops/sysfs)内核都写好了。
  • read_raw = 厨师:真正做菜——去 MPU6050 的寄存器读出数值。框架不会做你这道菜(它不懂你芯片的寄存器),只有你会。
  • 没有 read_raw 会怎样:属性文件还在,但用户 cat 时框架没厨师可喊,端不出任何数据。read_raw 是数值的唯一来源。
  • 为什么是回调:你不自己调它,而是把它登记给框架(iio_info.read_raw);用户一点菜,框架就回调它(控制反转)。
  • 参数就是点菜单:框架传 chan(哪个通道)和 mask(要 raw 还是 scale),你照单取值写回 *val。所以一个 read_raw 用 switch 就能应付所有通道、所有类型。
static int mpu6050_read_raw(indio_dev, chan, *val, *val2, mask) {
    data = iio_priv(indio_dev);         // 取回私有数据(拿 regmap)
    switch (mask) {                     // 内核要哪类值?
    case RAW:   按 chan->type 选寄存器 → regmap 读 → *val = ... ; return IIO_VAL_INT;
    case SCALE: 按 chan->type 返回换算系数;
    case OFFSET:返回温度偏置;
    }
}
记住:框架管"接待和上菜"(通用,内核写好);read_raw 管"做这道菜"(芯片相关,只有你会)。没有它,客人点了菜却没人做。

三、数据流与物理换算

cat in_accel_x_raw
  → IIO 核心(服务员)
  → 回调你的 read_raw(厨师)
  → regmap 读芯片 0x3B/0x3C
  → 返回原始值 → 内核格式化 → 用户看到数字

驱动只给原始值和换算系数,真正的单位换算由用户态按 IIO 约定完成:

  • 加速度(m/s²) = in_accel_x_raw × in_accel_scale
  • 角速度(rad/s) = in_anglvel_x_raw × in_anglvel_scale
  • 温度(℃) = (in_temp_raw + in_temp_offset) / 340

实测(假芯片预置 1g 时):in_accel_z_raw = 16384,× 0.000598550 ≈ 9.806 m/s²,正好是一个重力加速度。
