一、一段话总结整个流程

设备出现(由设备树或 i2c-stub + new_device 把硬件登记到 I2C 总线)→ i2c-core 用 compatible 或名字把"设备"和"驱动"匹配上 → 匹配成功后内核自动调用驱动的 probe() → probe 里完成三件事:① 用 devm_iio_device_alloc 分配 iio_dev + 私有数据;② 用 regmap 建立寄存器访问通道、读 WHO_AM_I 认芯片、唤醒;③ 填好 iio_dev 并 devm_iio_device_register 注册,挂上通道与 read_raw 回调。此后用户 cat 某个通道属性时,IIO 核心回调 read_raw,驱动用 regmap 现读芯片寄存器、把值写回并经 sysfs 返回给用户。

一句话:驱动是一座"待命 → 被匹配 → 在 probe 里开好柜台 → 被回调时现取现供"的桥。

二、驱动文件的主要内容(按书写/阅读顺序)

一个标准 i2c + IIO 驱动文件,主体就是下面这几块,顺序基本固定:

#组成部分作用(一句话)
1头文件 + 寄存器宏引入 module/i2c/regmap/iio;定义芯片寄存器地址
2struct 私有数据存这台设备自己的状态(regmap 句柄、配置…)
3regmap_config告诉 regmap 寄存器几位、数据几位
4通道数组 iio_chan_spec[]声明"能测什么量",决定生成哪些 sysfs 属性
5read_raw 回调用户读某通道时,去芯片取数据返回(按 mask 分 RAW/SCALE)
6struct iio_info回调表,把 read_raw 交给 IIO 核心
7probe()分配 → 初始化(regmap/WHO_AM_I/唤醒)→ 注册 IIO
8匹配表 id_table / of_match_table声明"我认得哪些设备"
9struct i2c_driver + module_i2c_driver驱动"名片"并注册到 i2c 总线
10MODULE_*许可、作者、描述
书写顺序建议:先写 1、8、9、10 搭空骨架让 probe 空跑通 → 再往 probe(7)里按"分配→初始化→注册"增量填 → 最后写 4、5、6 让数据能被读出来。每填一块就编译加载验证一次。

三、数据到底存在哪里(重点)

初学者最容易糊涂的是"传感器的数据到底存在驱动里的哪个变量"。答案是:测量数据根本不存在驱动里。要分三处看(图 1)。

  • ① 测量数据(加速度值)→ 住在芯片寄存器(如 0x3B 起)。由硬件实时更新。驱动不保存副本,每次被读时用 regmap 现读现返回。
  • ② 驱动的持久状态 → 住在内核堆的"私有数据" struct mpu6050_data。它和 iio_dev 由 devm_iio_device_alloc 一整块分配在内核堆;里面存的是 regmap 句柄、配置等"怎么访问芯片"的信息,不是测量值。用 iio_priv() 存取。
  • ③ 读出来的值 → 只是 read_raw 里的瞬时 *val。读一次、写回一次,不留存;内核把它格式化成字符串经 sysfs 交给用户。
所以 data->regmap 存的不是数据,是"读数据的通道";真正的数据在芯片里,读出来的值是过路的瞬时值。这也是为什么这个(direct 模式)驱动里没有一个"保存加速度的数组"——不需要,现读即可。(若要连续高速采集,才用"触发缓冲"在内核里开 kfifo,那是进阶内容。)

附录　三个关键结构体

驱动里反复出现三个指针:i2c_client *client、iio_dev *indio_dev、regmap *regmap。搞懂它们各代表什么、从哪来、存在哪,代码就不再是"黑话"。

A. struct i2c_client *client —— "总线上这颗具体芯片"的把手

  • 代表什么:挂在某条 I2C 总线上的一个具体从设备(就是你的 MPU6050)。
  • 从哪来:设备出现时由 i2c 核心创建并作为参数传进你的 probe(client, id)。你不分配它。
  • 关键字段:
    • client->addr —— 7 位从设备地址(如 0x68)。
    • client->adapter —— 它挂在哪条 I2C 总线(适配器);实际收发经它。
    • client->dev —— 内嵌的通用 struct device:打日志 dev_info(&client->dev, ...)、申请 devm 资源、取设备树节点都用它。
    • client->irq —— 该设备的中断号(若接了中断)。
  • 你怎么用它:把它交给 devm_regmap_init_i2c(client, &cfg) 建 regmap;用 &client->dev 做各种 devm_/日志调用。
  • 一句话:client = "驱动和这颗具体芯片对话的把手"(在哪条总线、什么地址)。

B. struct iio_dev *indio_dev —— "一个 IIO 设备"的登记表

  • 代表什么:IIO 子系统眼里的一个传感器设备;是你和 IIO 核心之间的句柄。
  • 从哪来:devm_iio_device_alloc(&client->dev, sizeof(私有数据)) 分配(连同私有数据一整块)。
  • 你要填的关键字段:
    • ->name —— 设备名(=> /sys/.../name)。
    • ->modes —— 工作模式,如 INDIO_DIRECT_MODE(直接读)。
    • ->info —— 指向 iio_info 回调表(含 read_raw)。
    • ->channels / ->num_channels —— 通道数组与数量(能测什么量)。
  • 内部(你不直接碰):它内部带着"私有数据区"(用 iio_priv(indio_dev) 取)和设备模型的 struct device。
  • 注册后:对应 /sys/bus/iio/devices/iio:deviceN。
  • 一句话:indio_dev = "把你的传感器登记进 IIO 的那张表 + 一块随它分配的私有数据"。

C. struct regmap *regmap —— 读写寄存器的"抽象句柄"

  • 代表什么:一条"读写某芯片寄存器"的抽象通道。它把"读/写寄存器"与具体总线(I2C/SPI)解耦。
  • 为什么叫"抽象":struct regmap 是不透明类型——它的内部字段定义藏在内核内部,你拿到的只是一个指针,不能直接访问它的成员,只能通过函数操作它:
    • regmap_read(regmap, reg, &val) / regmap_write(regmap, reg, val)
    • regmap_update_bits(regmap, reg, mask, val)(只改某几位)
    • regmap_bulk_read(regmap, reg, buf, n)(连读多个)
    注意:这些 API 第一个参数永远是 regmap 句柄——意思是"在这条通道上做这件事"。
  • 从哪来:devm_regmap_init_i2c(client, &mpu6050_regmap_config)。它内部记住了 client(走哪条总线、哪个地址)和 config(reg_bits/val_bits/max_register)。
  • 存在哪:regmap 对象本身也在内核堆(devm 分配、自动释放);你把它的指针存进私有数据 data->regmap,probe 存、read_raw 取。
  • 一句话:regmap = "一个只给你函数、不给你内部的读写通道把手";你调 regmap_read,它底层替你发 I2C 事务。
三者关系:client(哪颗芯片)→ 用它建 regmap(怎么读写这颗芯片)→ regmap 指针存进 indio_dev 的私有数据 → read_raw 回调里用 iio_priv(indio_dev) 取回 regmap 去读芯片。
